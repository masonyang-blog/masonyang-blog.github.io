1一、 大上下文的技術迷思與認知坍塌

[Direct Answer]
  1. 1為什麼百萬 Token 上下文窗口無法直接解決大型軟體工程的架構複雜度？
  2. 2Softmax 注意力稀釋如何導致代理人發生中段資訊遺忘與規範失效？
  3. 3多輪滾動長會話如何產生指數級累積的複利計費懲罰與歷史回饋污染？
[Support Details]深入數據推導、制度邊界與鏈上流動性實證分析

[Direct Answer] 軟體工程領域目前瀰漫著對百萬級上下文窗口（Long Context Window）的盲目崇拜。模型供應商透過行銷宣傳將「百萬 Token 吞吐」塑造為通用智能的終極解答，試圖讓開發者相信系統複雜度可以透過無限追加輸入長度直接抹平。這種工程怠惰正在生產巨大的隱性技術債與財務黑洞。

[Support Details]

1.1 注意力退化與 Needle-in-a-Haystack 的深層陷阱

Transformer 架構的注意力矩陣計算本質上是全局權重分配過程。當輸入上下文從數千 Token 暴增至數十萬 Token 時，模型對關鍵約束的檢索精度必然呈現顯著衰減：

$$\text{Attention}(Q, K, V) = \text{softmax}\left(\frac{QK^T}{\sqrt{d_k}}\right)V$$

隨著上下文長度 $N$ 擴增，Softmax 分母中的指數和項急劇累積，導致長距離注意力權重分佈被海量無關資訊稀釋。實驗與工業現場反覆驗證的客觀規律顯示：

  1. 1
    中段資訊遺忘（Lost in the Middle）：模型對位於 Context 核心中段的約束指令識別率驟降 30% 以上。
  2. 2
    雜訊放大效應（Noise Amplification）：全量代碼中包含的無關函式註解、過期歷史與邊緣邏輯，會成為注意力機制的干擾源，指數級推高隨機幻覺的發生率。
  3. 3
    架構規範失效：在超過 80,000 Token 的會話環境中，代理人開始出現「遺忘命名規範」、「私自繞過測試門禁」與「覆蓋未授權模組」等行為失控現象。

1.2 滾動會話的複利計費懲罰

雲端大模型的商業計費模式嚴格錨定於 Token 數量。在未經架構治理的傳統 Agent 運作模式中，每一次工具調用、每一筆錯誤回報與每一次輸出，都會以滾動累積的形式成為下一次推論的輸入前綴。

假設一個包含 10 個步驟的重構任務，若基礎 Context 在第 1 步即達到 30,000 Token，且每步產生 5,000 Token 的輸出與工具日誌，到了第 10 步時，單次 API 調用的輸入成本將達到：

$$\text{Input Tokens}_{\text{Step } 10} = 30,000 + (10 - 1) \times 5,000 = 75,000 \text{ Tokens}$$

整場任務累計消耗的輸入 Token 總量呈現階乘級發散，最終帳單支出將是實際有效邏輯價值的數十倍。資本分配的效率在此處遭遇嚴重扭曲。

1.3 認知漂移與錯誤假設的持久化污染

滾動長會話不僅帶來財務損失，更直接瓦解代碼品質。自主代理人在探索階段產生的無效假設、失敗的語法嘗試以及暫存的中間日誌，若未被即刻物理清除，將長久駐留在會話歷史中。模型具備強烈的自回歸延續傾向，極易將歷史中失敗的推論路徑視為合法上下文，形成反向回饋污染，導致後續修復行動陷入死循環。

2二、 架構支柱一Skills 路由式按需掛載

[Direct Answer] 消除 Token 浪費的第一道防線在於拆解全域常駐 System Prompt，建立輕量級路由索引與動態按需加載機制。

+-------------------------------------------------------------------+
                    |                        System Initial State                       |
                    |               (GEMINI.md + rules.md: ~1,200 Tokens)               |
                    +-------------------------------------------------------------------+
                                                      |
                                                      | [User Intent Analysis]
                                                      v
                    +-------------------------------------------------------------------+
                    |                        Router & Skill Index                       |
                    |   - Pulse Automation      -> skills/pulse-publisher/SKILL.md      |
                    |   - Task Protocol         -> skills/task-protocol/SKILL.md        |
                    |   - Web Standards         -> skills/dev-standards/SKILL.md        |
                    |   - Writing & Persona     -> skills/mason-writing-work/SKILL.md   |
                    +-------------------------------------------------------------------+
                                                      |
                                                      | [Dynamic view_file / Load on Demand]
                                                      v
                    +-------------------------------------------------------------------+
                    |                     Isolated Execution Context                    |
                    |        Only 1 targeted SKILL.md active (~800 - 1,500 Tokens)      |
                    +-------------------------------------------------------------------+

[Support Details]

2.1 傳統單體 System Prompt 的架構缺陷

多數團隊習慣將所有開發規範、編程風格、資料庫 Schema、SEO 準則與部署腳本全部集中寫入單一大型 System Prompt 中。此種作法導致任何微小任務（例如修正單一 CSS 屬性）都必須強行承擔上萬 Token 的靜態資訊負載。靜態基線直接吃掉對話視窗的有效配額，造成極高的基礎營運摩擦力。

2.2 雙層路由與意圖觸發機制

本系統推行的解決方案將架構嚴格劃分為「憲法層」與「技能層」：

  1. 1
    憲法核心（Constitutional Rules）：僅保留不可違背的底線邏輯（如零建置約束、最小改動原則、繁體中文規範），將全局常駐上下文壓縮在 1,500 Token 以內。
  2. 2
    規則路由器（`rules.md`）：建立精簡的意圖對照表，僅列出觸發關鍵字、職責邊界與目標路徑。
  3. 3
    按需掛載（Dynamic Skills）：將具體業務規格（如新聞發布管線、樣式審計、數據庫架構）封裝為獨立的 `SKILL.md`。當且僅當當前任務明確涉及特定領域時，Agent 才透過單次檔案讀取精準掛載對應模組。

這種解耦設計使靜態上下文基礎消耗常態性下降 60% 至 75%，確保模型注意力在任務啟動之初保持最高純度。

2.3 主流 AI 寫程式環境的落地映射：Cursor 與 Antigravity 的工程實踐

這套按需架構在主流 AI 寫程式工具與 Agent 環境中具備直接的工程對應實作：

  • Cursor 寫程式環境適配：在 Cursor 中，許多團隊傾向在 `.cursorrules` 或 `.cursor/rules/*.mdc` 中塞入全部業務規格，導致每次對話強制灌入龐大上下文。更優解法是將 `.cursor/rules` 視為單一指引指針，配合專案級入口 `AGENTS.md` 建立階層導航鏈，將規格全數下沉至獨立的 Markdown 文件與技能庫，唯有在偵測到特定開發意圖時才導向讀取。
  • Google Antigravity 寫程式環境適配：在 Antigravity 體系中，利用 `.agents/rules.md` 作為中央路由器，將具體工作流封裝於 `.agents/skills/[skill_name]/SKILL.md`，並透過 YAML Frontmatter 宣告觸發詞（triggers）與單一真理源依賴（ssot_dependencies）。Agent 啟動時僅載入憲法檔案（`GEMINI.md`），隨後由內建技能發現機制按需調用 `view_file` 載入專屬技能，徹底切斷無效資訊傳播路徑。

3三、 架構支柱二工具鏈脫水防火牆

[Direct Answer] 即使成功控制靜態提示詞，若允許 Agent 在代碼庫內肆意執行全量檔案讀取，上下文視窗依然會在數秒內被淹沒。脫水防火牆（Dehydration Firewall）的核心精神在於：嚴禁任何未經結構化篩選的原始文本流入模型推論空間。

[Support Details]

3.1 Code Skeleton：基於 AST 的結構提煉

面對超過 150 行的大型原始碼檔案，傳統的直接讀取方式會導入大量的具體函式實作細節，而 Agent 在探索架構與函式簽名時，這類實作細節純屬雜訊。

透過部署專用 AST 提煉腳本（`tools/code_skeleton.py`），系統將原始碼中的函式本體全部替換為語法佔位符，僅保留類別聲明、公用介面、型別註解與頂層 Docstring：

# tools/code_skeleton.py 核心邏輯展示
                    class SkeletonTransformer(ast.NodeTransformer):
                        def visit_FunctionDef(self, node):
                            node.body = [ast.Expr(value=ast.Constant(value="..."))]
                            return node

                        def visit_AsyncFunctionDef(self, node):
                            node.body = [ast.Expr(value=ast.Constant(value="..."))]
                            return node

以一個包含 1,200 行代碼的後端控制器為例：

  • 原始全檔讀取：約需消耗 8,400 Tokens。
  • AST 骨架提煉：僅需消耗 720 Tokens。
  • 單點脫水效率：直接削減 91.4% 的探索雜訊。

3.2 Repo Radar：大綱探測與精準標靶切片

對於長篇規格文件、Markdown 報告或大型 HTML 結構，系統依賴 `tools/repo_radar.py` 實施二階段探詢法：

  1. 1
    階段一：大綱錨定（Outline Mode）：僅掃描文件標題層級（H1/H2/H3）與行號分布，產生幾十行的高度壓縮索引。
  2. 2
    階段二：標靶切片（Section Mode）：Agent 根據大綱鎖定特定區塊，僅截取目標標題下的有效段落（範圍通常在 20 至 50 行之間）。

這種做法徹底終結了「為查看一個表格而加載 2,000 行文檔」的低效操作，將常規文件讀取的 Token 損耗穩定鎖定在 800 Tokens 以下。

3.3 RTK 終端指令過濾與輸出脫水

終端執行環境（Bash / PowerShell）往往伴隨大量的終端控制碼、重複進度條、套件安裝日誌與重複性堆疊追蹤。全量回傳這些內容會迅速耗盡上下文配額。

透過在指令前綴包裝原生過濾器（`rtk`），系統在輸出端實施物理脫水：

  • 自動剔除 ANSI 顏色代碼與進度條字元。
  • 壓縮連續重複的成功日誌，僅保留 Exit Code 與末尾摘要。
  • 遭遇錯誤時，精確截取 Exception 核心與最後 15 行堆疊，壓制非關鍵資訊。

4四、 架構支柱三One Phase, One Session 物理隔絕

[Direct Answer] 前兩大支柱解決了單次互動的資訊密度問題，而第三大支柱則從根本上阻斷跨步驟歷史堆積的複利效應。

Phase 1: 架構重構與 SSOT 定義
                    +-----------------------------------------------------------+
                    | Session 1                                                 |
                    | [Input: rules.md + task_*.md]                             |
                    | -> 執行驗證 (Exit 0)                                      |
                    | -> 更新實體 task_*.md (標記已完成)                        |
                    | -> 強制物理停步，會話終結 (Context 銷毀)                  |
                    +-----------------------------------------------------------+
                                                   |
                                                   | [無狀態實體傳遞：唯一依據為磁碟上的 task_*.md]

4.1 物理隔絕原則（Physical Isolation）

「One Phase, One Session」是一條不可妥協的工程底線。任何大型專案必須在實體任務檔（`task_*.md`）中被原子化切分為多個離散階段（Phase）。每個階段的執行必須獨佔一個乾淨的會話環境：

  1. 1
    單一會話推進單一階段：Agent 嚴格專注於當前 Phase 的目標與驗收標準。
  2. 2
    驗證達標即刻停步：當前階段的所有單元驗收通過後，最後一步必須是更新實體任務檔並提交 Checkpoint，隨後立即交回終端控制權。
  3. 3
    禁止跨階段連鎖執行：嚴禁在同一個對話中連續推進下一個 Phase。

4.2 實體任務檔作為唯一真理源（SSOT）

在物理隔絕架構下，跨會話的狀態傳遞不再依賴 LLM 不可靠的滾動記憶，而是完全依託持久化於磁碟中的實體任務檔。

  • 新 Session 啟動時，Agent 僅需透過精準切片讀取 `task_*.md` 中當前待辦的 Phase 規格。
  • 上一會話中所有繁雜的調試軌跡、工具調用細節與探索嘗試被徹底拋棄，會話歷史被硬性歸零。
  • 此機制完全消除了上下文漂移的物理基礎，賦予系統具備無限階段擴展的架構韌性。

6.1 資本分配視角：Token 即算力資本

在工業級軟體開發中，Token 消耗不應被視為廉價的消耗品，而應被視為高昂的算力資本配置。

  • 無節制地將整個代碼庫塞入提示詞，本質上是開發者放棄架構設計職責的惰性表現。
  • 每一筆冗餘 Token 的傳輸，都在稀釋注意力矩陣對核心業務邏輯的聚焦能力。
  • 追求極致的資訊密度（Information Density）是軟體架構永恆的第一性原理。在有限的上下文預算內傳遞最具結構確定性的訊息，才是衡量資深工程能力的核心標尺。

6.2 抽象層洩漏與供應商激勵解構

雲端模型供應商的商業激勵與終端企業的工程利益存在本質上的錯位：

  • 供應商的激勵路徑：推廣更大的上下文窗口、鼓勵用戶上傳未加工的文件與代碼，從而按 Token 計費獲取最大化的雲端推論營收。
  • 企業工程師的生存路徑：追求最小成本、最快響應速度與最高執行確定性。

若工程師全盤接受「大上下文解決一切」的宣傳敘事，將直接掉入供應商精心構建的計費陷阱中。脫水防火牆與按需架構的存在，正是工程師奪回主權、建立確定性防線的技術手段。

6.3 演化劇本：從規模擴張走向微架構內斂

展望未來的自主代理人技術演進：

  • 路徑 A（外延式擴張）：繼續依賴硬體算力堆疊更大參數與更長上下文，但邊際收益將迅速觸碰物理牆與注意力瓶頸。

7.1 Repo Radar 標靶切片演算法 (Python)

import re
                    import sys

                    def parse_markdown_outline(filepath: str):
                        """提取 Markdown 標題層級與對應行號，產生緊湊大綱"""
                        with open(filepath, 'r', encoding='utf-8') as f:
                            lines = f.readlines()

                        outline = []
                        for idx, line in enumerate(lines, 1):
                            match = re.match(r'^(#{1,4})\s+(.+)$', line)
                            if match:
                                level = len(match.group(1))
                                title = match.group(2).strip()
                                outline.append(f"L{idx:<4} | {'  ' * (level - 1)}{title}")
                        return "\n".join(outline)

                    if __name__ == "__main__":
                        if len(sys.argv) > 1:
                            print(parse_markdown_outline(sys.argv[1]))
